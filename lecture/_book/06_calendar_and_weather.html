6  Calendar features and real weather data

NoteLearning objective

You can set up an ExogBuilder with cyclic RBF features, read real weather data from Open-Meteo via the WeatherService class, and concatenate both into a single feature matrix that is later passed to the forecaster as exogenous input.

6.1 Why does the model need more than the load itself?

The load depends not only on its own immediate history but also on context information: time of day, day of week, holiday, weather. If the model only sees “Wednesday 18:00” and “Wednesday 02:00” as hours 18 and 2, it has no way to recognise that these hours stand in a cyclic relationship to each other and repeat periodically. We encode such cyclic features with radial basis functions (RBF) so that an hour is always similar to its neighbouring hours — including the midnight transition.

Weather is the second pillar. In cold weather the load rises (heating, lighting); on sunny summer days it falls. The model therefore sees per hour a tuple of hourly temperature, cloud cover, precipitation and wind speed. The Open-Meteo API provides these values both retrospectively (archive) and prospectively (forecast) without an API key.

6.2 AI Act link

Art. 10(1) of the AI Act requires that “training, validation and testing data sets […] meet the quality criteria laid down in paragraphs 2 to 4”. One of the quality requirements is representativeness: the model must have seen all relevant seasonal, calendar-related and weather-dependent variations. By training the load jointly with calendar and weather features, we practically deliver the “examination of statistically probable characteristics” demanded by Art. 10(2)(f).

WeatherService enforces code rule CR-3: any gap in the weather data that remains after resampling is reported as ValueError — not silently filled.

6.3 Code in action: cyclic calendar features

import pandas as pd
from pathlib import Path
from spotforecast2_safe import Period, ExogBuilder

shared = Path("_cache/shared")
y_train = pd.read_parquet(shared / "y_train.parquet")["load"]
y_eval  = pd.read_parquet(shared / "y_eval.parquet")["load"]

periods = [
    Period(name="hour",      n_periods=12, column="hour",      input_range=(0, 23)),
    Period(name="dayofweek", n_periods=4,  column="dayofweek", input_range=(0,  6)),
    Period(name="month",     n_periods=12, column="month",     input_range=(1, 12)),
]
builder = ExogBuilder(periods=periods, country_code="DE")
exog_cal = builder.build(y_train.index.min(), y_eval.index.max())

print(f"Calendar features: {exog_cal.shape[0]:,} hours, {exog_cal.shape[1]} columns")
print(f"Columns:           {list(exog_cal.columns)[:6]} ...")
Calendar features: 8,040 hours, 30 columns
Columns:           ['hour_0', 'hour_1', 'hour_2', 'hour_3', 'hour_4', 'hour_5'] ...
import matplotlib.pyplot as plt

day = exog_cal.loc["2024-03-04 00:00":"2024-03-04 23:00"]
fig, ax = plt.subplots(figsize=(8.5, 3.0))
hour_cols = [c for c in day.columns if c.startswith("hour_")]
for c in hour_cols:
    ax.plot(range(24), day[c].values, linewidth=1.0, alpha=0.7)
ax.set_xticks(range(0, 24, 2))
ax.set_xlabel("Hour of day")
ax.set_ylabel("RBF activation")
ax.set_title("12 cyclic basis functions for the hour of day")
ax.grid(True, color="#E5E5E5", linewidth=0.5)
for s in ("top", "right"):
    ax.spines[s].set_visible(False)
fig.tight_layout()
plt.show()

6.4 Code in action: weather

For a central German location — Frankfurt am Main, a typical load centre — we fetch the hourly values. The WeatherService class handles the cache transparently: the first request goes to the API, subsequent identical requests are served from the parquet file.

from spotforecast2_safe.weather import WeatherService

cache = Path("_cache") / "weather_de_2024.parquet"
ws = WeatherService(
    latitude=50.110924,
    longitude=8.682127,
    cache_path=cache,
    use_forecast=False,         # historical data only - we stay in 2024
)
weather = ws.get_dataframe(
    start=y_train.index.min(),
    end=y_eval.index.max(),
    freq="h",
    fill_missing=False,         # CR-3: fail-safe, no silent imputation
)
print(f"Weather frame: {weather.shape[0]:,} hours, {weather.shape[1]} columns")
print(f"First columns: {list(weather.columns)[:5]} ...")
print(f"NaN values:    {int(weather.isna().sum().sum())} (should be 0; otherwise CR-3 would have aborted)")
Weather frame: 8,040 hours, 15 columns
First columns: ['temperature_2m', 'relative_humidity_2m', 'precipitation', 'rain', 'snowfall'] ...
NaN values:    0 (should be 0; otherwise CR-3 would have aborted)

6.6 Concatenating calendar and weather into a single matrix

The load and the exogenous columns must have exactly the same index, otherwise the forecaster later fails. This is a direct consequence of CR-3: missing index rows would silently become NaN inside pandas — and that is exactly what we want to avoid.

exog = exog_cal.join(weather, how="inner")
exog = exog.loc[y_train.index.min(): y_eval.index.max()]

print(f"Joined feature matrix: {exog.shape[0]:,} hours, {exog.shape[1]} columns")
print(f"NaN values:            {int(exog.isna().sum().sum())}")

exog.to_parquet(shared / "exog.parquet")

## Concatenating calendar and weather into a single matrix

The load and the exogenous columns must have exactly the same index,
otherwise the forecaster later fails. This is a direct consequence of
**CR-3**: missing index rows would silently become NaN inside `pandas`
--- and that is exactly what we want to avoid.

```{python}
#| label: merge-exog
#| echo: true
exog = exog_cal.join(weather, how="inner")
exog = exog.loc[y_train.index.min(): y_eval.index.max()]

print(f"Joined feature matrix: {exog.shape[0]:,} hours, {exog.shape[1]} columns")
print(f"NaN values:            {int(exog.isna().sum().sum())}")
```
