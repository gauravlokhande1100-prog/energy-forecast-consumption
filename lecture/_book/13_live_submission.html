13  Live submission to the ddmo-sose-26 challenge

NoteLearning objective

You can generate today’s 24-hour DE load forecast with the production pipeline (spotforecast2 + spotforecast2-safe), write a validated submission CSV in the exact schema the leaderboard expects, and open the pull request that puts your team on the live ranking at https://bartzbeielstein.github.io/challenge-leaderboard/.

13.1 Overview

Previous chapters walked through every stage of the pipeline against a frozen 2024 evaluation window. That deterministic, reproducible sandbox is exactly what the EU AI Act asks for in the development phase. This final chapter is different in two ways: the data is today’s, and the target is y_0 (tomorrow), not a held-out 2024 window. Everything else, i.e., the safety contracts, the assertions, and the fail-loudly semantics, carries over.

13.2 Submission contract

The leaderboard repository challenge-leaderboard accepts one CSV per team per day with the following exact shape:

File path: submissions/team_4_optuna/<YYYY-MM-DD>.csv — the filename is the target day (the day being forecast), not the submission day. Deadline: D-1 23:59 UTC (the validator rejects later PRs). Scoring: per-day mean absolute error in MW (MAE = (1/24) Σ |ŷ_h − y_h|). Public ranking: rolling 7-day mean MAE, smallest wins; ties broken first by cumulative MAE, then by number of valid submissions.

The implementation is auditable. The load-bearing contract anchors are published on github.com (https://github.com/bartzbeielstein/challenge-leaderboard/tree/main/scripts) and visible in the codebase:

  • validate_schema() at scripts/validate_submission.py:53
  • validate_deadline() at scripts/validate_submission.py:79
  • score_submission() at scripts/score_day.py:112
  • aggregate() at scripts/build_leaderboard.py:35
  • The daily scoring cron at .github/workflows/score-daily.yml:5

13.4 Step-by-step student walkthrough

13.4.1 Prerequisites

Python 3.13 with uv for environment management, git and the GitHub CLI (gh) authenticated as your registered handle, a personal ENTSO-E Transparency Platform API key (free; request via My Account Settings → Web API Security Token), and about 1 GB of free disk for the cached interim ENTSO-E CSV.

13.4.2 Step 1: Clone the lecture and fork the leaderboard

Assume git@git-ce.rwth-aachen.de:spotseven-lab/ddmo-sose-26.git as the lecture repo URL. The forked leaderboard is where you write your submission CSV and open the PR; the lecture repo is where you run the pipeline and render this chapter.

mkdir -p ~/workspace && cd ~/workspace
git clone git@git-ce.rwth-aachen.de:spotseven-lab/ddmo-sose-26.git ddmo-sose-26
gh repo fork bartzbeielstein/challenge-leaderboard --clone --remote

The fork lets you push your submission branch without write access to the upstream. Your PR will come from bartzbeielstein/challenge-leaderboard:submission/team_4_optuna-<YYYY-MM-DD>-<HHMMSS> into bartzbeielstein/challenge-leaderboard:main.

cd ~/workspace/ddmo-sose-26

This installs spotforecast2-safe>=13.4.1, spotforecast2>=2.2.2, and the rest of the dependencies into a local .venv/. Quarto reads QUARTO_PYTHON to find this interpreter (see the lecture’s Makefile).

export ENTSOE_API_KEY="<your-personal-key-from-transparency.entsoe.eu>"

The live cells below read the key from the environment, never from a hard-coded literal in the rendered HTML.

13.4.5 Step 4: Set your team id

This chapter uses the registered team team_4_optuna throughout. The TEAM_ID constant lives in the submission write cell at Section 13.5; edit it once if you adapt the chapter for a different team.

Render this chapter (make render at the lecture root, or just quarto render lecture/13_live_submission.qmd). The render writes a real CSV at ~/workspace/challenge-leaderboard/submissions/team_4_optuna/<tomorrow>.csv.

13.4.8 Step 7: Open the submission PR

cd ~/workspace/challenge-leaderboard
TARGET=<YYYY-MM-DD>            # e.g. tomorrow's UTC date
# Unique branch per attempt (avoids colliding with an earlier merged branch
# if you re-submit for the same target day).
BRANCH="submission/team_4_optuna-${TARGET}-$(date -u +%H%M%S)"
git switch -c "$BRANCH" main
git add "submissions/team_4_optuna/${TARGET}.csv"
git commit -m "submission(team_4_optuna): forecast for ${TARGET}"
git push -u origin "$BRANCH"
gh pr create --base main --repo bartzbeielstein/challenge-leaderboard \
    --head "$BRANCH" \
    --title "submission(team_4_optuna): forecast for ${TARGET}" \
    --body "Generated by the ddmo-sose-26 live submission chapter."

If validation passes, auto-merge squashes the submission onto main. The next morning at 07:00 UTC, score-daily.yml scores it against ENTSO-E final actuals and the leaderboard refreshes within a minute.

WarningDeadline

Submissions for target day D must be merged before D-1 23:59 UTC — the validator enforces this strictly. The full pipeline (render → validate → push → PR → auto-merge) typically completes in under two minutes, but ENTSO-E API hiccups during the data refresh can occasionally cost a few more. Submit at least 30 minutes before the deadline to leave yourself recovery room.

13.5.1 Dynamic date constants

Every date is derived from pd.Timestamp.now(tz="UTC").normalize() so the chapter stays correct on every render. The convention follows the canonical bart26b/CLAUDE.md Date-range rule:

  • y_{-1} = yesterday’s 24 hourly DE Actual Load values (UTC day D-1)
  • ŷ_{-1} = the model’s prediction for the same window (used by chapters 08–10 as the scorable exemplar)
  • y_0 = today’s 24 h (UTC day D); the real live target — not scorable until ~D+1 06:00 UTC when ENTSO-E publishes final actuals
NOW_UTC = pd.Timestamp.now(tz="UTC")

13.5.3 Determine the live training cutoff and forecast horizon

At submission time the ENTSO-E intra-day actuals usually cover only part of today, so we cannot anchor end_train_default at today 23:00 UTC. Instead we anchor at the latest hour for which Actual Load is non-NaN, floor it to a clean hour boundary, and compute how many hourly forecast steps we need to reach the end of tomorrow. After training we slice tomorrow’s 24 hourly steps out of the longer forecast — those are the y_0 rows we submit.

LAST_TARGET = TOMORROW_UTC + pd.Timedelta(hours=23)
LAST_FULL_HOUR = interim["Actual Load"].dropna().index.max().floor("h")
FIRST_PRED = LAST_FULL_HOUR + pd.Timedelta(hours=1)
LIVE_N_STEPS = int((LAST_TARGET - FIRST_PRED).total_seconds() // 3600) + 1

print(f"end_train (inclusive): {LAST_FULL_HOUR}")
print(f"first forecast step  : {FIRST_PRED}")
print(f"last forecast step   : {LAST_TARGET}")
print(f"predict_size         : {LIVE_N_STEPS}  (slice last 24 for y_0)")
end_train (inclusive): 2026-05-31 19:00:00+00:00
first forecast step  : 2026-05-31 20:00:00+00:00
last forecast step   : 2026-06-01 23:00:00+00:00
predict_size         : 28  (slice last 24 for y_0)
NoteWhy is predict_size usually larger than 24?

predict_size is not “how many hours we want to submit.” It is the number of hourly steps the recursive forecaster must produce, starting at the first hour after the last known actual, until it reaches the end of tomorrow. The 24 rows we submit are then sliced out of that longer forecast.

The math, step by step:

\[ \begin{aligned} \texttt{FIRST\_PRED} &= \texttt{LAST\_FULL\_HOUR} + 1\,\text{h} \\ \texttt{LAST\_TARGET} &= \texttt{TOMORROW\_UTC} + 23\,\text{h} \\ \texttt{LIVE\_N\_STEPS} &= \frac{\texttt{LAST\_TARGET} - \texttt{FIRST\_PRED}}{1\,\text{h}} + 1 \end{aligned} \]

The + 1 is because both endpoints are inclusive (we need the hour FIRST_PRED and the hour LAST_TARGET).

Decomposing the horizon into two segments makes it obvious where the extra steps come from:

\[ \underbrace{\texttt{LIVE\_N\_STEPS}}_{\text{total recursion}} = \underbrace{(24 - \texttt{LAST\_FULL\_HOUR.hour} - 1)}_{\text{bridge: rest of today}} + \underbrace{24}_{y_0:\text{ tomorrow}} \]

A worked example. Suppose the chapter is rendered at 18:30 UTC and ENTSO-E’s intra-day feed currently publishes Actual Load through 17:00 UTC today. Then:

  • LAST_FULL_HOUR = today 17:00 UTC
  • FIRST_PRED = today 18:00 UTC
  • LAST_TARGET = tomorrow 23:00 UTC
  • bridge hours = 24 - 17 - 1 = 6 (today 18:00, 19:00, 20:00, 21:00, 22:00, 23:00)
  • target hours = 24 (tomorrow 00:00 … 23:00)
  • LIVE_N_STEPS = 6 + 24 = 30

Why can’t we just ask the model for 24 steps and start at tomorrow 00:00? Because the LightGBM forecaster behind entsoe_lgbm_factory is recursive: its feature row for hour \(h+1\) uses the lag-1 value \(\hat{y}_h\) that it produced one step earlier (together with lag-2, lag-24, calendar, and weather features). It cannot “jump” over the 6 bridge hours; each prediction is built from the chain of preceding predictions. The bridge hours are scaffolding the recursion needs to reach tomorrow — once it has, the next cell slices them off:

y0 = future.loc[TOMORROW_UTC:LAST_TARGET]   # exactly 24 rows

So LIVE_N_STEPS floats with how fresh ENTSO-E’s feed happens to be at render time:

Render time (UTC) LAST_FULL_HOUR Bridge hours LIVE_N_STEPS
00:30 (feed current through 23:00 of previous day) yesterday 23:00 24 (all of today) 48
12:30 (feed current through 11:00) today 11:00 12 36
18:30 (feed current through 17:00) today 17:00 6 30
23:30 (feed current through 22:00) today 22:00 1 25
just after midnight (feed already current through 23:00 of previous day) yesterday 23:00 24 48

The submission CSV still has exactly 24 rows in every case — only the amount of throwaway bridge forecasting changes.

13.5.4 Build the live ConfigEntsoe

All inputs to the pipeline travel on a single configuration object. The hooks (data_loader, test_data_loader, forecaster_factory) are the same ones the bart26b publication uses. The training-window parameters and tuning budgets follow the canonical defaults. The ConfigEntsoe documentation is at https://sequential-parameter-optimization.github.io/spotforecast2-safe/docs/reference/configurator.config_entsoe.ConfigEntsoe.html

We pass cv_block_size=PREDICT_SIZE (= 24) so the rolling cross-validation scores a fixed 24-hour-ahead block, decoupled from the render-dependent live horizon predict_size=LIVE_N_STEPS. Chapter 14 derives why this matters at Section 14.6.2.

TRAIN_SIZE = pd.Timedelta(days=365 * 3)
PREDICT_SIZE = 24
REFIT_SIZE = 7
NUMBER_FOLDS = 10
DELTA_VAL = pd.Timedelta(hours=PREDICT_SIZE * REFIT_SIZE * NUMBER_FOLDS)

live_config = ConfigEntsoe(
    country_code="DE",
    data_filename="interim/energy_load.csv",
    targets=["Actual Load"],
    agg_weights=[1.0],
    bounds=[(-1e9, 1e9)],
    data_loader=entsoe_data_loader,
    test_data_loader=entsoe_test_data_loader,
    forecaster_factory=entsoe_lgbm_factory,
    periods=[Period(name='daily', n_periods=12, column='hour', input_range=(1, 24))],
    lags_consider=[1, 2, 24],
    train_size=TRAIN_SIZE,
    end_train_default=LAST_FULL_HOUR.isoformat(),
    delta_val=DELTA_VAL,
    predict_size=LIVE_N_STEPS,
    cv_block_size=PREDICT_SIZE,
    refit_size=REFIT_SIZE,
    n_trials_optuna=30,
    n_trials_spotoptim=7,
    n_initial_spotoptim=5,
    random_state=42,
    on_weather_failure="skip",
)
live_config.data_frame_name = "ddmo-live"
print("live_config ready:", live_config.data_frame_name,

### Determine the live training cutoff and forecast horizon

At submission time the ENTSO-E intra-day actuals usually cover only part
of today, so we cannot anchor `end_train_default` at today 23:00 UTC.
Instead we anchor at the latest hour for which `Actual Load` is
non-NaN, floor it to a clean hour boundary, and compute how many hourly
forecast steps we need to reach the end of tomorrow. After training we
slice tomorrow's 24 hourly steps out of the longer forecast — those are
the `y_0` rows we submit.

```{python}
#| label: live-cutoff
#| echo: true
LAST_TARGET = TOMORROW_UTC + pd.Timedelta(hours=23)
LAST_FULL_HOUR = interim["Actual Load"].dropna().index.max().floor("h")
FIRST_PRED = LAST_FULL_HOUR + pd.Timedelta(hours=1)
LIVE_N_STEPS = int((LAST_TARGET - FIRST_PRED).total_seconds() // 3600) + 1

print(f"end_train (inclusive): {LAST_FULL_HOUR}")
print(f"first forecast step  : {FIRST_PRED}")
print(f"last forecast step   : {LAST_TARGET}")
print(f"predict_size         : {LIVE_N_STEPS}  (slice last 24 for y_0)")
```

::: {.callout-note title="Why is `predict_size` usually larger than 24?"}
`predict_size` is **not** "how many hours we want to submit." It is the
number of hourly steps the recursive forecaster must produce, starting
at the first hour *after* the last known actual, until it reaches the
end of tomorrow. The 24 rows we submit are then *sliced out of* that
longer forecast.

The math, step by step:

$$
\begin{aligned}
\texttt{FIRST\_PRED}  &= \texttt{LAST\_FULL\_HOUR} + 1\,\text{h} \\
\texttt{LAST\_TARGET} &= \texttt{TOMORROW\_UTC} + 23\,\text{h} \\
\texttt{LIVE\_N\_STEPS} &= \frac{\texttt{LAST\_TARGET} - \texttt{FIRST\_PRED}}{1\,\text{h}} + 1
\end{aligned}
$$

The `+ 1` is because both endpoints are inclusive (we need the hour
`FIRST_PRED` *and* the hour `LAST_TARGET`).

Decomposing the horizon into two segments makes it obvious where the
extra steps come from:

$$
\underbrace{\texttt{LIVE\_N\_STEPS}}_{\text{total recursion}}
= \underbrace{(24 - \texttt{LAST\_FULL\_HOUR.hour} - 1)}_{\text{bridge: rest of today}}
+ \underbrace{24}_{y_0:\text{ tomorrow}}
$$

A worked example. Suppose the chapter is rendered at 18:30 UTC and
ENTSO-E's intra-day feed currently publishes `Actual Load` through
**17:00 UTC** today. Then:

- `LAST_FULL_HOUR`  = today 17:00 UTC
- `FIRST_PRED`     = today 18:00 UTC
- `LAST_TARGET`    = tomorrow 23:00 UTC
- bridge hours     = `24 - 17 - 1 = 6` (today 18:00, 19:00, 20:00, 21:00, 22:00, 23:00)
- target hours     = 24 (tomorrow 00:00 … 23:00)
- `LIVE_N_STEPS`   = `6 + 24 = 30`

Why can't we just ask the model for 24 steps and start at tomorrow
00:00? Because the LightGBM forecaster behind `entsoe_lgbm_factory` is
**recursive**: its feature row for hour $h+1$ uses the lag-1 value
$\hat{y}_h$ that it produced one step earlier (together with lag-2,
lag-24, calendar, and weather features). It cannot "jump" over the 6
bridge hours; each prediction is built from the chain of preceding
predictions. The bridge hours are scaffolding the recursion needs to
reach tomorrow — once it has, the next cell slices them off:

```python
y0 = future.loc[TOMORROW_UTC:LAST_TARGET]   # exactly 24 rows
```

So `LIVE_N_STEPS` floats with how fresh ENTSO-E's feed happens to be at
render time:

| Render time (UTC) | `LAST_FULL_HOUR` | Bridge hours | `LIVE_N_STEPS` |
|:--|:--|--:|--:|
| 00:30 (feed current through 23:00 of *previous* day) | yesterday 23:00 | 24 (all of today) | 48 |
| 12:30 (feed current through 11:00) | today 11:00 | 12 | 36 |
| 18:30 (feed current through 17:00) | today 17:00 | 6 | 30 |
| 23:30 (feed current through 22:00) | today 22:00 | 1 | 25 |
| just after midnight (feed already current through 23:00 of *previous* day) | yesterday 23:00 | 24 | 48 |

The submission CSV still has exactly 24 rows in every case — only the
amount of throwaway bridge forecasting changes.
:::

### Local validation with the leaderboard's own script

A green exit code from `validate_submission.py` is the same check that
runs on the PR in CI. We pass `--skip-deadline` because the chapter may
be rendered inside the deadline window (the live CI uses the strict
form without the flag).

```{python}
#| label: live-validate
#| echo: true
import subprocess
lb_repo = Path.home() / "workspace" / "challenge-leaderboard"
result = subprocess.run(
    [
        "uv", "run", "python", "scripts/validate_submission.py",
        "--path", str(submission_path.relative_to(lb_repo)),
        "--skip-deadline",
    ],
    cwd=lb_repo,
    capture_output=True,
    text=True,
)
print("exit code:", result.returncode)
print("stdout   :", result.stdout.strip())
if result.stderr.strip():
    print("stderr   :", result.stderr.strip())
```

## What the render did NOT do {#sec-live-not-rendered}

The cells above only write the CSV. They do not commit, push, or open a
PR — those are deliberate operator steps so a careless render cannot
spam the leaderboard. The bash recipe in @sec-live-walkthrough step 7
is the manual hand-off; once the PR is opened, the leaderboard's CI
(see @sec-live-cron) takes over.

## Tomorrow's scoring {#sec-live-cron}

The leaderboard's daily cron is configured at `.github/workflows/score-daily.yml:5`:

```
cron: "0 7 * * *"
```

That is 07:00 UTC every day. The cron fetches ENTSO-E final actuals for
yesterday (= the target day of the submission you just opened), computes
per-team MAE, opens a bot PR that updates `data/scores.parquet`, and
triggers `build-and-deploy.yml` which republishes
<https://bartzbeielstein.github.io/challenge-leaderboard/>. End-to-end
latency from your PR merge to a refreshed leaderboard row is typically
under 90 seconds after `D+1 07:00 UTC`.
