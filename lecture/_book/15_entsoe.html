15  ENTSO-E day-ahead baseline submission

NoteLearning objective

You can submit the transmission system operators’ own 24-hour DE load forecast — ENTSO-E’s published day-ahead Forecasted Load — as a zero-model baseline on the live leaderboard, under the registered team entsoe. The chapter shows why this baseline is the honest yardstick every tuned forecaster in Chapter 13 and Chapter 14 must beat, and writes the validated CSV into the leaderboard fork.

15.1 Overview

Chapter 13 tunes an Optuna LightGBM forecaster; Chapter 14 tunes a richer SpotOptim variant. Both pull ENTSO-E’s own day-ahead Forecasted Load purely as a comparison overlay (Section 14.6.11) and never let the model train on it. This chapter inverts that relationship: it submits ENTSO-E’s day-ahead forecast directly, with no model at all.

That is deliberate. ENTSO-E aggregates the forecasts the European transmission system operators already produce for grid scheduling, so it is a strong, free, professionally-maintained baseline. A tuned model that cannot beat it over the rolling 7-day window is not earning its compute. Submitting it as its own team entsoe puts that yardstick on the public leaderboard next to the student models, where the comparison is unavoidable.

Every safety contract from Chapter 13 carries over unchanged (24-row schema, strictly-positive forecasts, no NaN). What disappears is the entire modelling stack: no MultiTask, no ConfigEntsoe, no tuning, no exogenous features. The forecast is a slice of the downloaded ENTSO-E frame. Two wrinkles specific to a forward baseline are handled along the way — the safe downloader drops future rows unless asked to keep them (Section 15.5.2), and a UTC target day straddles two local publication days (Section 15.5.3).

15.2 Submission contract

Unchanged — see Section 13.2 for the CSV schema, deadline, and scoring rules. The leaderboard validator that runs against this chapter’s output is byte-identical to the one used by Chapter 13. The only difference is the path: submissions/entsoe/<YYYY-MM-DD>.csv.

15.5.1 Dynamic date constants

Every date is derived from pd.Timestamp.now(tz="UTC").normalize() so the chapter stays correct on every render — same convention as Section 13.5. y_0 is tomorrow’s UTC day (00:00–23:00 UTC), the 24 hourly stamps the leaderboard scores.

NOW_UTC = pd.Timestamp.now(tz="UTC")
TODAY_UTC = NOW_UTC.normalize()
TOMORROW_UTC = TODAY_UTC + pd.Timedelta(days=1)
LAST_TARGET = TOMORROW_UTC + pd.Timedelta(hours=23)

# A day-ahead baseline needs no training history --- only a short recent window:
# enough to carry the last week of `Actual Load` for the context plot plus a
# previous-day fallback (@sec-entsoe-extract). We download the last 10 days and
# reach the end through the day *after* tomorrow so the full target day is
# covered as soon as ENTSO-E publishes it. download_new_data takes the window as
# 'YYYYMMDDHH00' strings.
START_DOWNLOAD = (TODAY_UTC - pd.Timedelta(days=10)).strftime("%Y%m%d%H%M")
END_DOWNLOAD = (TOMORROW_UTC + pd.Timedelta(days=1)).strftime("%Y%m%d%H%M")

15.5.2 Download ENTSO-E’s day-ahead Forecasted Load

We fetch through the same safe wrapper the training chapters use, spotforecast2_safe.downloader.entsoe.download_new_data, with one argument that matters here: keep_forecast_future=True. By default the wrapper drops every row after now when it merges the download into the interim file —

# spotforecast2_safe/downloader/entsoe.py
if not keep_forecast_future:
    merged_df = merged_df.loc[merged_df.index <= pd.Timestamp.now(tz="UTC")]

That truncation is correct for the training chapters (a model must never see the future), but it would erase the very thing this baseline submits: ENTSO-E’s day-ahead Forecasted Load for tomorrow. The flag keeps those future rows; future Actual Load is still blank, so nothing leaks — there is no model here in any case. ENTSO-E’s Forecasted Load is published per local (Europe/Berlin) day; the wrapper normalises the merged interim index to UTC, the zone the leaderboard scores in.

download_new_data(
    api_key=api_key,
    country_code="DE",
    start=START_DOWNLOAD,
    end=END_DOWNLOAD,
    force=True,
    keep_forecast_future=True,   # keep tomorrow's day-ahead forecast
)

interim_csv = get_data_home() / "interim" / "energy_load.csv"

15.5.3 Assemble the 24-hour target slice

The target is the 24 UTC hours of tomorrow, 00:00 … 23:00. ENTSO-E publishes its day-ahead forecast per local (Europe/Berlin) day, and Germany runs one or two hours ahead of UTC. So at submission time — the afternoon of D-1, when only the local D day-ahead is out — the last one or two UTC hours of the target (22:00, 23:00 UTC) fall into the next local day, which ENTSO-E does not publish until D, after the D-1 23:59 UTC deadline.

Those trailing hours are therefore filled with ENTSO-E’s own forecast for the same clock hour 24 hours earlier — a transparent, fully reproducible persistence of the operators’ published forecast (today’s day-ahead is already complete, so the fallback source always exists). The fill is logged, and a fail-loud guard (CR-3) aborts if even the fallback is missing rather than writing a short or NaN-padded CSV.

target_index = pd.date_range(TOMORROW_UTC, LAST_TARGET, freq="h", tz="UTC")  # 24 stamps
y0 = forecast_h.reindex(target_index)

published = int(y0.notna().sum())
missing = y0.index[y0.isna()]
print(f"day-ahead hours published for {TOMORROW_UTC.date()}: {published} / 24")

for ts in missing:
    fallback = forecast_h.reindex([ts - pd.Timedelta(days=1)]).iloc[0]
    if pd.isna(fallback):
        raise RuntimeError(
            f"No day-ahead value for {ts} and no 24 h-earlier fallback either; "
            "ENTSO-E coverage is too thin to assemble 24 hours. Re-render once "
            "the day-ahead forecast for the target day is published."
        )
    y0.loc[ts] = fallback
    print(f"  filled {ts} ← {ts - pd.Timedelta(days=1)} (24 h-earlier ENTSO-E forecast = {fallback:,.0f} MW)")

y0.name = "Forecasted Load"
print(f"\ny_0 assembled: {len(y0)} hourly steps | {y0.index.min()} → {y0.index.max()}")
print(y0)

15.6 Commit and push the submission PR

The cells above only write the CSV — they deliberately do not commit, push, or open the PR (a careless render must not be able to spam the leaderboard). Run the block below from a shell once the validation cell above is green:

cd ~/workspace/challenge-leaderboard
# TARGET=$(date -u -d 'tomorrow' +%F)                # Linux equivalent
TARGET=$(date -u -v+1d +%F)
# Unique branch per attempt: re-submitting for the same target day must not
# collide with an earlier (already-merged) branch of the same name.
BRANCH="submission/entsoe-${TARGET}-$(date -u +%H%M%S)"
git switch -c "$BRANCH" main
git add "submissions/entsoe/${TARGET}.csv"
git commit -m "submission(entsoe): day-ahead baseline for ${TARGET}"
git push -u origin "$BRANCH"

gh pr create --base main --repo bartzbeielstein/challenge-leaderboard \
    --head "$BRANCH" \
    --title "submission(entsoe): day-ahead baseline for ${TARGET}" \
    --body  "Generated by ddmo-sose-26 chapter 15 (ENTSO-E day-ahead baseline)."

If validation on the PR passes, auto-merge squashes the submission onto main. The next morning at 07:00 UTC the leaderboard’s score-daily.yml cron (see Section 13.7) scores it against ENTSO-E final actuals.

WarningDeadline

Submissions for target day D must be merged before D-1 23:59 UTC — the validator enforces this strictly. This baseline renders in seconds, but the local D day-ahead Forecasted Load is only published around midday D-1; render after that window so the bulk of the 24 target hours come straight from the feed and only the one or two UTC/local boundary hours rely on the fallback.

15.7 Why a baseline team

The leaderboard ranks on rolling 7-day mean MAE (Section 13.2). Without a reference point, a student team has no way to tell whether an MAE of, say, 1500 MW is good. The entsoe row supplies that reference: it is the accuracy the operators’ own forecast achieves on the very same scoring rule. Three readings follow directly from its position on the board:

  • A team above entsoe is beating the professional day-ahead forecast — a genuine result worth writing up.
  • A team below entsoe is being out-predicted by a free public series and should revisit features or tuning before adding compute.
  • entsoe’s own day-to-day MAE variance shows the irreducible difficulty of each target day — a calm Sunday scores tighter than a volatile cold snap, for everyone.

### Dynamic date constants

Every date is derived from `pd.Timestamp.now(tz="UTC").normalize()` so the
chapter stays correct on every render --- same convention as @sec-live-example.
`y_0` is tomorrow's UTC day (00:00–23:00 UTC), the 24 hourly stamps the
leaderboard scores.

```{python}
#| label: entsoe-constants
#| echo: true
NOW_UTC = pd.Timestamp.now(tz="UTC")
TODAY_UTC = NOW_UTC.normalize()
TOMORROW_UTC = TODAY_UTC + pd.Timedelta(days=1)
LAST_TARGET = TOMORROW_UTC + pd.Timedelta(hours=23)

# A day-ahead baseline needs no training history --- only a short recent window:
# enough to carry the last week of `Actual Load` for the context plot plus a
# previous-day fallback (@sec-entsoe-extract). We download the last 10 days and
# reach the end through the day *after* tomorrow so the full target day is
# covered as soon as ENTSO-E publishes it. download_new_data takes the window as
# 'YYYYMMDDHH00' strings.
START_DOWNLOAD = (TODAY_UTC - pd.Timedelta(days=10)).strftime("%Y%m%d%H%M")
END_DOWNLOAD = (TOMORROW_UTC + pd.Timedelta(days=1)).strftime("%Y%m%d%H%M")

print(f"NOW_UTC        = {NOW_UTC}")
print(f"TODAY_UTC      = {TODAY_UTC}")
print(f"TOMORROW_UTC   = {TOMORROW_UTC}  (target day = y_0)")
print(f"LAST_TARGET    = {LAST_TARGET}")
print(f"START_DOWNLOAD = {START_DOWNLOAD}  (10 days back --- no training history)")
print(f"END_DOWNLOAD   = {END_DOWNLOAD}  (covers tomorrow's day-ahead forecast)")
```

### Download ENTSO-E's day-ahead `Forecasted Load` {#sec-entsoe-query}

We fetch through the same safe wrapper the training chapters use,
`spotforecast2_safe.downloader.entsoe.download_new_data`, with one argument
that matters here: `keep_forecast_future=True`. By default the wrapper drops
every row after `now` when it merges the download into the interim file ---

```python
# spotforecast2_safe/downloader/entsoe.py
if not keep_forecast_future:
    merged_df = merged_df.loc[merged_df.index <= pd.Timestamp.now(tz="UTC")]
```

That truncation is correct for the training chapters (a model must never see
the future), but it would erase the very thing this baseline submits: ENTSO-E's
day-ahead `Forecasted Load` for tomorrow. The flag keeps those future rows;
future `Actual Load` is still blank, so nothing leaks --- there is no model
here in any case. ENTSO-E's `Forecasted Load` is published per *local*
(Europe/Berlin) day; the wrapper normalises the merged interim index to UTC,
the zone the leaderboard scores in.

```{python}
#| label: entsoe-query
#| echo: true
download_new_data(
    api_key=api_key,
    country_code="DE",
    start=START_DOWNLOAD,
    end=END_DOWNLOAD,
    force=True,
    keep_forecast_future=True,   # keep tomorrow's day-ahead forecast
)

interim_csv = get_data_home() / "interim" / "energy_load.csv"
interim = pd.read_csv(interim_csv, index_col=0, parse_dates=True)
interim.index = pd.to_datetime(interim.index, utc=True)

print(f"interim rows       : {len(interim)} (15-min, {interim.index.min()} → {interim.index.max()})")
print(f"columns            : {list(interim.columns)}")
print(f"Forecasted Load to : {interim['Forecasted Load'].dropna().index.max()}")
print(f"Actual Load to     : {interim['Actual Load'].dropna().index.max()}")
```

We aggregate the 15-minute series onto the hourly grid the leaderboard scores
on --- the mean of each hour's four quarter-hour values, matching how the
tuned chapters aggregate the actuals.

```{python}
#| label: entsoe-hourly
#| echo: true
forecast_h = interim["Forecasted Load"].resample("h").mean().dropna()
actual_h = interim["Actual Load"].resample("h").mean().dropna()
forecast_h.name = "Forecasted Load"
actual_h.name = "Actual Load"

print(f"hourly forecast : {len(forecast_h)} h | {forecast_h.index.min()} → {forecast_h.index.max()}")
print(f"hourly actual   : {len(actual_h)} h | {actual_h.index.min()} → {actual_h.index.max()}")
```

### Assemble the 24-hour target slice {#sec-entsoe-extract}

The target is the 24 UTC hours of tomorrow, `00:00 … 23:00`. ENTSO-E publishes
its day-ahead forecast per *local* (Europe/Berlin) day, and Germany runs one
or two hours ahead of UTC. So at submission time --- the afternoon of `D-1`,
when only the local `D` day-ahead is out --- the last one or two UTC hours of
the target (`22:00`, `23:00` UTC) fall into the *next* local day, which ENTSO-E
does not publish until `D`, after the `D-1 23:59 UTC` deadline.

Those trailing hours are therefore filled with ENTSO-E's own forecast for the
same clock hour 24 hours earlier --- a transparent, fully reproducible
persistence of the operators' published forecast (today's day-ahead is already
complete, so the fallback source always exists). The fill is logged, and a
fail-loud guard (CR-3) aborts if even the fallback is missing rather than
writing a short or NaN-padded CSV.

```{python}
#| label: entsoe-extract
#| echo: true
target_index = pd.date_range(TOMORROW_UTC, LAST_TARGET, freq="h", tz="UTC")  # 24 stamps
y0 = forecast_h.reindex(target_index)

published = int(y0.notna().sum())
missing = y0.index[y0.isna()]
print(f"day-ahead hours published for {TOMORROW_UTC.date()}: {published} / 24")

for ts in missing:
    fallback = forecast_h.reindex([ts - pd.Timedelta(days=1)]).iloc[0]
    if pd.isna(fallback):
        raise RuntimeError(
            f"No day-ahead value for {ts} and no 24 h-earlier fallback either; "
            "ENTSO-E coverage is too thin to assemble 24 hours. Re-render once "
            "the day-ahead forecast for the target day is published."
        )
    y0.loc[ts] = fallback
    print(f"  filled {ts} ← {ts - pd.Timedelta(days=1)} (24 h-earlier ENTSO-E forecast = {fallback:,.0f} MW)")

y0.name = "Forecasted Load"
print(f"\ny_0 assembled: {len(y0)} hourly steps | {y0.index.min()} → {y0.index.max()}")
print(y0)
```

## Commit and push the submission PR {#sec-entsoe-push}

The cells above only *write* the CSV --- they deliberately do not commit,
push, or open the PR (a careless render must not be able to spam the
leaderboard). Run the block below from a shell once the validation cell above
is green:

```bash
cd ~/workspace/challenge-leaderboard
# TARGET=$(date -u -d 'tomorrow' +%F)                # Linux equivalent
TARGET=$(date -u -v+1d +%F)
# Unique branch per attempt: re-submitting for the same target day must not
# collide with an earlier (already-merged) branch of the same name.
BRANCH="submission/entsoe-${TARGET}-$(date -u +%H%M%S)"
git switch -c "$BRANCH" main
git add "submissions/entsoe/${TARGET}.csv"
git commit -m "submission(entsoe): day-ahead baseline for ${TARGET}"
git push -u origin "$BRANCH"

gh pr create --base main --repo bartzbeielstein/challenge-leaderboard \
    --head "$BRANCH" \
    --title "submission(entsoe): day-ahead baseline for ${TARGET}" \
    --body  "Generated by ddmo-sose-26 chapter 15 (ENTSO-E day-ahead baseline)."
```

If validation on the PR passes, auto-merge squashes the submission onto
`main`. The next morning at 07:00 UTC the leaderboard's `score-daily.yml` cron
(see @sec-live-cron) scores it against ENTSO-E final actuals.

::: {.callout-warning title="Deadline"}
Submissions for target day `D` must be merged before `D-1 23:59 UTC` --- the
validator enforces this strictly. This baseline renders in seconds, but the
local `D` day-ahead `Forecasted Load` is only published around midday `D-1`;
render after that window so the bulk of the 24 target hours come straight from
the feed and only the one or two UTC/local boundary hours rely on the fallback.
:::

## Why a baseline team {#sec-entsoe-why}

The leaderboard ranks on rolling 7-day mean MAE (@sec-live-contract). Without
a reference point, a student team has no way to tell whether an MAE of, say,
1500 MW is good. The `entsoe` row supplies that reference: it is the accuracy
the operators' own forecast achieves on the very same scoring rule. Three
readings follow directly from its position on the board:

- A team *above* `entsoe` is beating the professional day-ahead forecast ---
  a genuine result worth writing up.
- A team *below* `entsoe` is being out-predicted by a free public series and
  should revisit features or tuning before adding compute.
- `entsoe`'s own day-to-day MAE variance shows the irreducible difficulty of
  each target day --- a calm Sunday scores tighter than a volatile cold snap,
  for everyone.
